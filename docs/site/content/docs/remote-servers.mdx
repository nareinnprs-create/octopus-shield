A Remote Shield Server lets one computer do the work while another computer provides the UI. The server keeps the projects, worktrees, terminals, tabs, provider accounts, and agent sessions. Your laptop connects to that running Shield instance.

The easiest setup is the Shield desktop app on both computers, connected through [Tailscale](https://tailscale.com/). You do not need to run `shield serve` for this path.

<Callout title="Beta">
  Remote Shield Servers are beta. Keep the server and client on a private network path you control,
  such as the same Tailscale tailnet or LAN.
</Callout>

## What runs where

```text
Client computer · Shield client
  Shows the UI and sends your input
                 │
                 │ private network route
                 ▼
Server computer · Shield server
  Stores repos and worktrees
  Runs terminals and agents
```

Install and authenticate Codex, Claude Code, OpenCode, `git`, and any provider CLIs on the **server computer**. A login on your laptop does not automatically carry over to the server.

On a headless `shield serve` host, register managed Claude/Codex accounts from the server shell (the remote client disables **Add account**):

```bash
shield account add --agent claude
shield account add --agent codex
shield account list
```

Install or refresh agent skills without a Settings UI:

```bash
shield skills install --skill shield-cli --skill orchestration
shield skills update --all
```

## Recommended: desktop app + Tailscale

You need:

- Shield installed and updated on both computers
- Tailscale installed on both computers
- Both computers signed in to the same tailnet
- The server computer awake, online, and running Shield

Tailscale gives the server a private address that usually starts with `100.`. Shield puts that address first in its connection-address picker.

### 1. Create an access link on the server

On the computer that should keep the sessions running:

1. Open the Shield desktop app.
1. Open **Settings → Remote Shield Servers**.
1. Under **Advertise this app as a server**, click **New Link**.
1. For **Connection address**, select the Tailscale address. It usually looks like `100.x.y.z`.
1. Click **Generate Access Link**.
1. Copy the link under **Pair another Shield client**.

If the Tailscale address is missing, confirm Tailscale is connected and click the refresh button beside **Connection address**.

<Callout title="Keep the access link private">
  The pairing URL grants access to this Shield runtime. Treat it like a password and send it only to
  the client you intend to pair.
</Callout>

### 2. Add the server on your laptop

On the computer you want to use as the client:

1. Open **Settings → Remote Shield Servers**.
1. Click **Add Server**.
1. Enter a recognizable name, such as `Remote Server`.
1. Paste the access link from the server.
1. Click **Add Server**.
1. If the saved server shows **Disconnected**, click **Connect**.

Adding a server saves it without forcing every new project onto it. Open **Advanced → Default host for new projects** only when you want server-routed projects, terminals, provider checks, and browser or mobile handoff to use that server by default.

## Use the remote server

Once the server shows **Connected**, select it or one of its projects and use Shield normally. Terminals, agent processes, files, worktrees, and session state live on the server computer.

When several paired clients share that server, the sidebar filter can offer **Hide other-client workspaces** so this device only lists workspaces it created. See [Worktrees → Sidebar layout](/docs/model/worktrees#sidebar-layout).

That means:

- agents keep running when the client laptop sleeps or disconnects;
- the server needs the repository, tools, and credentials used by those agents;
- the server must stay awake and connected to the tailnet;
- reconnecting the client or reopening Shield returns you to the server-owned workspace, tab, and visible-pane state without duplicating paired tabs;
- projects you delete on the server disappear from every paired client's sidebar (no permanent ghost rows).

## Access and security

Shield creates a separate, revocable token for each paired client. The server lists these under **Shared Server Access**.

- Click the trash button beside a grant to revoke it. Active clients using that grant are disconnected immediately.
- Generating another link replaces the previous **unused** link. Clients that already paired keep their own grants until you revoke them.
- Keep Tailscale ACLs or grants as narrow as your setup allows.
- Do not forward the Shield port directly to the public internet. Prefer Tailscale, WireGuard, a trusted LAN, SSH forwarding, or an authenticated tunnel.
- Do not select `127.0.0.1` for another computer. That address only works on the server itself.

## Alternative: `shield serve`

Use `shield serve` when the host should run without the desktop window—for example, a headless Linux server or a service-managed VM. For a MacBook or desktop you can leave signed in, the in-app setup above is simpler.

Install Shield and its bundled CLI on the server, then run:

<Callout title="On Linux, start it with shield-ide serve">
  The Linux CLI is named `shield-ide`, because GNOME Shield's screen reader already owns
  `/usr/bin/shield`. A packaged `shield serve` does write a bare `shield` into `~/.local/bin`, but only
  while it is starting, so that shim can never be the command that starts the server. Read `shield
  serve` as `shield-ide serve` throughout this page when the host is Linux. See [Install →
  Linux](/docs/install#linux).
</Callout>

```bash
shield serve --pairing-address <server-tailscale-ip-or-hostname>
# Linux
shield-ide serve --pairing-address <server-tailscale-ip-or-hostname>
```

For example:

```bash
shield serve --pairing-address 100.64.1.20
# Linux
shield-ide serve --pairing-address 100.64.1.20
```

The command:

- starts the Shield runtime without opening the desktop window;
- on macOS, stays out of the Dock and the Cmd-Tab switcher until you open a desktop window from it;
- runs in the foreground until you press `Ctrl-C`;
- prints the bound endpoint and a runtime pairing URL;
- uses `--pairing-address` only for the address clients should dial.

Paste the printed pairing URL into **Settings → Remote Shield Servers → Add Server** on the client.

Add `--port 6768` when a firewall, tunnel, or service definition requires a fixed port:

```bash
shield serve --port 6768 --pairing-address 100.64.1.20
# Linux
shield-ide serve --port 6768 --pairing-address 100.64.1.20
```

Use only one host mode at a time. If the Shield desktop app is already sharing that computer, do not start a second `shield serve` process for the same setup.

`shield serve` runs on Shield's own Node server (octopod) by default. If octopod can't serve on this computer, it uses the desktop app's server instead and prints one line saying why. On a packaged macOS app it currently always uses the desktop app's server, so paired clients can still update it. To always use the desktop app's server, set `OSHIELD_SERVE_RUNTIME=electron`.

### Limit terminal memory on a Linux server

By default, nothing caps how much memory a terminal's processes use, so one runaway job can push the whole server into the kernel's out-of-memory killer. On Linux you can cap each terminal by setting these variables in the environment that starts `shield serve` (or in its service unit):

```bash
export OSHIELD_TERMINAL_MEMORY_MAX=16G      # memory per terminal, 256M or more
export OSHIELD_TERMINAL_MEMORY_SWAP_MAX=0   # swap per terminal; 0 means no swap
shield-ide serve --pairing-address 100.64.1.20
```

- Each terminal already runs in its own systemd user scope. The limits become that scope's `MemoryMax` and `MemorySwapMax`.
- When a terminal goes over its limit, the kernel kills its largest process. Typically that is the job, and the shell keeps running. The server and every other terminal keep running.
- The limits are off by default because Shield can't know what a sensible limit is for your workloads.
- They need systemd with cgroup v2 and a user manager that outlives logout (`loginctl enable-linger <user>`). If the host can't enforce a limit, Shield skips it, logs `terminal-memory-limits` in the terminal host log, and starts terminals without it.
- Shield reads them only when its terminal host process starts. That process keeps running when `shield serve` restarts, so terminals keep their old limits until it restarts too, for example after the server reboots.
- They have no effect on macOS or Windows.

### Use the GPU on a Linux server

On Linux, `shield serve` turns off hardware acceleration by default, because most headless hosts have no GPU and a failing GPU process can stop the server from starting. Browser panes then render in software. If the host gives the Shield process a GPU (for example a render node such as `/dev/dri/renderD128`), set `OSHIELD_SERVE_GPU=1` in the environment that starts `shield serve` (or in its service unit) to keep hardware acceleration on:

```bash
export OSHIELD_SERVE_GPU=1
shield-ide serve --pairing-address 100.64.1.20
```

This only stops Shield from turning the GPU off. Chromium may still render in software on Shield's own Xvfb, which has no GPU of its own; open `chrome://gpu` in a browser pane to check, and point `DISPLAY` at a GPU-backed X server if it reports software rendering. If you installed the server with `shield serve service install`, add the variable to the service unit yourself. If the server stops starting or browser panes crash with it set, unset it to go back to software rendering.

### Mobile from a headless server

For the Shield mobile app, request a mobile-scoped QR code and link:

```bash
shield serve --pairing-address 100.64.1.20 --mobile-pairing
# Linux
shield-ide serve --pairing-address 100.64.1.20 --mobile-pairing
```

Keep the phone on the same tailnet, open Shield Mobile, choose **Pair**, and scan the terminal QR code or paste the printed link.

## Desktop app or `shield serve`?

|               | Desktop app on the server           | `shield serve`                                       |
| ------------- | ----------------------------------- | -------------------------------------------------- |
| Best for      | An old laptop, Mac mini, or desktop | A headless Linux box, VM, or managed service       |
| Setup         | Settings and buttons                | Terminal command and service configuration         |
| Server window | Open                                | None                                               |
| Access link   | **New Link → Generate Access Link** | Printed in the terminal                            |
| Lifetime      | While the desktop app is running    | While the foreground process or service is running |

## Remote Shield Server or SSH?

Use [SSH worktrees](/docs/ssh) when Shield on your laptop should own the runtime and use another machine only to run selected worktrees and terminals.

Use a Remote Shield Server when the other machine should own the full Shield runtime and preserve shared sessions for desktop, browser, mobile, or automation clients.

See [Ways to run Shield](/docs/ways-to-run) for the full comparison.

## Troubleshooting

### The Tailscale address is not listed

On the server, confirm Tailscale is connected, then click the refresh button beside **Connection address**. Both computers must be signed in to the same tailnet. A Tailscale IPv4 address usually starts with `100.`.

### The server is disconnected

Confirm the server computer is awake, Shield is still running, and Tailscale shows both devices online. Check your tailnet ACLs or grants if one device cannot reach the other.

Update Shield on both computers if the server row reports an incompatible protocol version.

### The access link was shared with the wrong person

On the server, open **Settings → Remote Shield Servers → Shared Server Access** and revoke that grant. Generate a new link for the intended client.

### The server cannot find an agent CLI

Install and authenticate that CLI on the server computer. Remote sessions use the server's `PATH`, home directory, and credentials—not the client's.

### `shield serve` advertises the wrong address

Stop the command and restart it with an address the client can reach:

```bash
shield serve --pairing-address <reachable-tailscale-ip-or-hostname>
```

Do not use a wildcard address or `127.0.0.1` for a remote client.
